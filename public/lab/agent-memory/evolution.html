第 05 章 · 经验与技能本地阅读

CHAPTER 05 / 经验与技能

过去的经历，
怎样帮助新的任务？

案例、规则、工作流与程序的复用接口，以及反馈、维护和迁移的不同要求。

状态 · 事实 · 经验
跨任务经验记忆要解决的，是让一次任务中付出的探索成本，在后续任务中继续产生价值。它可以保存具体案例、提炼决策规则，也可以留下工作流与可执行程序。这些形式各有用途：案例提供情境，规则帮助判断，程序承担重复执行。研究的关键，是解释经验怎样形成、经由什么接口改变行为，以及这种改变能迁移到哪里。
从重试到跨任务复用案例与规则反馈与归纳策略与程序持续积累迁移的条件

1. 同题反思与跨题学习：两个可以组合的回路

延续代码 Agent 的自拟例子：排障时发现“测试失败来自环境变量缺失”，可以立即修正环境再运行；也可以把诊断过程保存下来，供下次处理类似故障。前者改善本次尝试，后者改变未来任务的起点。记忆保存多久，不如它把哪次经验带给哪次决策更能说明学习发生在哪里。

Reflexion 将执行、评估和自我反思分开。执行者产生轨迹，评估器给出结果，反思器把结果与过程转成具体建议；下一次尝试同一任务时，建议与当前轨迹共同进入上下文。评估器可采用答案匹配、环境启发式或模型判断，记忆通常保留最近 1–3 次反思。这里语言建议承担的是稀疏反馈到下一次行动之间的桥梁。[3]

ExpeL 把桥梁延伸到未见任务：先在训练任务上借助重试收集经验，再从经验池提炼洞见、检索成功示例；测试时只尝试一次，也能利用先前练习。它因此把“练习时探索”与“执行时利用”分开。同题重试仍可叠加：论文在 ALFWorld 上观察到，ExpeL 的首次成功率为 59.0%，对未完成任务继续三轮反思后为 64.2%。这个组合说明，两种时间尺度可以同时贡献，而不是一条路线取代另一条。[8]

这种区分也决定怎样阅读实验：重试后的成功率衡量额外探索的效果，未见任务的首次成功率更直接反映经验迁移。比较方法时，应先确定经验来自训练集还是先前的测试任务，以及当前任务允许尝试几次，再讨论收益大小。

2. 案例与规则：保留情境，还是提炼共同结构？

具体案例保留问题、操作与环境的对应关系，适合回答“以前遇到相似情况时怎样处理”；一般规则则去掉实例细节，回答“这类情况应注意什么”。在代码排障中，完整调用链是一份案例，“先检查输入是否跨越协议边界”是一条策略。规则覆盖面可能更广，但案例能提供规则背后的条件，两者可以共同存在。

ExpeL 将两种对象放在同一系统中：按任务相似性检索成功轨迹作为示例；同时比较同题成功与失败轨迹，并从多题成功集合中抽取共同洞见。它不要求模型在“照着案例做”与“遵循一般原则”之间二选一。其消融提供了有解释力的差异：HotpotQA 更受益于洞见，ALFWorld 更受益于轨迹回忆，WebShop 则两者接近。有用的抽象粒度取决于任务需要重建什么。[8]

仅轨迹检索（retrieval-only）31%55%38%

原文 §5.2：问答需要可跨问题使用的推理指引，具身任务有较稳定的动作结构，购物任务兼有检索、比较和执行。表格是特定实验中的对照，不是不同表示的普遍排名。完整 ExpeL 同时使用两条路径。[8]

这一选择也贯穿相关工作。Synapse 先抽象页面状态，再检索观察—行动轨迹；AWM 将完整经历切成参数化子流程；ReasoningBank 则保存高层策略。它们分别减少观察噪声、实例绑定与重复推导的负担。这里不宜画“轨迹越来越短，记忆越来越好”的上升阶梯：删除细节的同时，也可能删除未来任务需要的适用条件。[9][13][17]

Contextual Experience Replay 又区分了经验中的两类内容：环境知识记录常用页面、页面用途及 URL，操作模式描述反复有效的决策方法；系统分别提炼、保存并检索它们。这个划分提醒我们，一条看似通用的“经验”可能依赖网站的稳定 URL 或特定工具行为。经验抽象时保留这些环境条件，比单纯追求更短的规则更有助于迁移。[16]

3. 从结果到经验：反馈必须与归纳对象匹配

一次测试通过能证明特定检查成功，却不直接给出值得推广的规则；一次失败也可能同时包含正确步骤与错误假设。因此经验形成至少有两步：确定观察到的结果，再提出解释和可复用建议。Reflexion 把反馈转为下一轮行动建议，ExpeL 用成功与失败的对照支撑跨任务洞见，它们让归纳建立在可以检查的经历上。[3][8]

ReasoningBank 面向没有参考答案的任务流：任务完成后，由模型判定代理性的成功或失败，再分别抽取策略与教训，写成标题、描述和内容组成的条目；后续任务检索相关条目进入系统提示。其 MaTTS 将额外推理同时用于生产记忆：并行尝试之间可比较不同路径，连续修正则提供中间错误与调整过程。这样，额外计算的产物既可能改善当前答案，也可能成为未来任务的经验。[17]

ReasoningBank 在 WebArena-Shopping 的消融中，使用成功与失败经历比仅成功经历从 46.5 提高到 49.7；同一比较中，直接把失败纳入 AWM 则没有相同收益。其含义是失败能形成有价值的策略，但需要适合失败的转换过程。成功流程回答怎样完成任务，失败教训回答应避免什么、在哪一步增加检查；把两者原样混入同一个示例库，未必能利用这种差异。[17]

近期的 Trace2Skill 进一步让失败分析器检查产物、对照参考结果并尝试验证修复，再提出技能补丁；成功分析器则提取可复用行为。它将反馈来源从轨迹文字扩展到可检查的任务产物。相应地，在线自评和离线验证是不同的学习条件：前者便于持续积累，后者能够为候选修改提供更强的约束。选择取决于部署中能获得什么信号。[26]

展开：为什么不能把更多反思等同于更多证据

ExpeL §5.6 中，正常洞见提取在 HotpotQA 达到 39.0% 成功率，额外输入反思文本的变体为 29.0%。作者认为反思中的幻觉可能误导更高层归纳。这支持保留原始轨迹与归纳解释的区别；并不说明语言反思普遍无效。ReasoningBank 的 judge 也提供代理标签，当前版本对校准噪声做了实验，其结果仍须放在所测任务与噪声模型内理解。[8][17]

4. 策略、工作流与程序：谁负责重新生成行动？

当一个子过程反复出现，复用可以从“给建议”扩展到“执行已有实现”。两者的关键差异是接口：文字策略与示例进入模型上下文，由模型结合新状态产生行动；可执行函数则封装部分行动，可以被新程序组合调用。名为 skill 的文件既可能是前一种，也可能包含后一种，不能按名称归为同一种机制。

AWM 把“购买某种猫粮”的经历切出“搜索商品”子流程，并将具体商品替换为 {product-name}。每步包含环境描述、推理与行动，默认作为辅助上下文供 Agent 使用。Voyager 则把 Minecraft 技能存为可执行代码，按描述检索已有函数，用它们构造新程序；程序经过环境反馈、执行异常和成功自验证的迭代后进入技能库。前者减少每次寻找流程的负担，后者进一步支持程序组合。[13][4]

AWM 将工作流中的代码动作改为自然语言后，整体效果没有显示稳定的大差距。这说明真正重要的变量并不只是文字或代码的表面格式，而是子过程粒度、状态信息以及调用方式。代码 Agent 可以保留“先定位再修改”的文字策略，同时复用一个确定性的 trace 解析脚本；需要实时观察的决策仍由执行者完成。[13]

Mem²Evolve 将这种互补做成双存储：经验库记录工具使用、生成与调试的经验，资产库保存工具实现与专家 Agent 配置。执行时优先复用，缺少能力时用经验指导创建，随后验证并保存新资产。其 GAIA 分析中，经验指导使新工具首次通过系统内部验证的比例从 32.7% 到 51.0%，平均修正轮次从 1.45 到 0.94。这个中间结果清楚展示了经验如何帮助形成可用能力；资产质量仍受验证覆盖约束。[20]

5. 持续积累：维护执行知识，也保存改进历史

把一条经验提炼得好，只解决了第一次写入。随着任务增多，系统还要决定如何合并重复建议、局部修订旧规则，以及保留已经尝试过的修改。ACE 将执行、反思与维护分工：Generator 使用 playbook，Reflector 从轨迹提炼洞见，Curator 产生条目级修改，由确定性逻辑合并。增量更新配合去重，减少整份提示反复重写造成的知识丢失。[18]

技能文档的优化也体现同一问题。Trace2Skill 并行分析多条轨迹，再层次化合并补丁，突出跨经历重复出现的模式；SkillOpt 则控制每轮编辑数量，以选择集分数决定是否接受，并保留拒绝编辑与跨轮经验。一个偏向批量编译，一个偏向有界迭代；二者都把任务经历转换成部署时可直接使用的技能，而不是要求执行者阅读所有原始日志。[26][27]

Memento-Skills 和 EvoSkill 进一步把“怎样挑选候选”显式化。Memento-Skills 结合参考答案反馈、自产测试与回滚来修改技能，并训练查询到技能的路由；EvoSkill 通过失败分析提出新技能，按验证分数维护有限的 top-k 候选程序。这里形成两种不同的评估需求：候选本身是否改善留出任务，以及部署时能否正确触发它。只测全文注入后的效果，不能替代技能路由的检验。[24][25]

WikiSkill 明确分离了知识的消费者：原始层保存不可变轨迹，wiki 层积累模式、提案历史和影响记录，skill 层提供执行时的程序性指令。技能提案未通过验证时，skill 回滚，wiki 中的调查结果却保留。由此，记忆可以通过帮助优化器提出更好的修改产生价值，不必全部进入最终执行者的上下文。[19]

论文的 ALFWorld 案例展示了这个过程：泛化的“目标导向行动”提案未改善验证表现，系统保留拒绝记录；下一轮改为“不要把物品送回原位置”的具体规则后被接受，后续又根据新轨迹细化操作约束。配套消融中，给提案者加入持久 wiki 管线带来明显改善。这里的设计认识是：改进过程本身也需要连续性，部署指令则需要保持明确。[19]

展开：局部更新与持久知识的证据边界

ACE Appendix A.5 的 AppWorld test-normal 对照：非增量更新的 TGC/SGC 为 67.3/46.4，增量更新为 76.2/64.3。WikiSkill Table 3 在执行者不读 wiki 时，加入 Maintainer 与提案者 wiki 访问后，四基准平均分从 48.7 到 63.7；两项组件一起变化，不能将全部收益单归因于文件结构。WikiSkill 将技能全文注入系统提示，主要检验形成的技能质量，没有同时检验大规模技能触发与路由。[18][19]

6. 迁移取决于知识、消费者和执行环境

经验价值最终表现为后续任务行为的改变。应分别问：迁移的是具体经历、一般策略还是程序？目标任务是否共享工具和状态结构？目标模型是否能执行这些指导？一个文件能够被复制，并不意味着其中的假设能在目标环境成立。

ExpeL 将 HotpotQA 的洞见迁移到 FEVER，两者共享 Wikipedia 检索接口，并通过目标任务示例改写指导，取得正向迁移。WikiSkill 的跨模型结果揭示另一个侧面：小模型在 OfficeQA 形成的技能对自身帮助有限，却能改善更强模型的表现。发现可用程序知识和实际执行这种知识，是可以分离的能力。相反，为小模型设计的细碎 workaround 也可能妨碍强模型，或消耗更多交互预算。[8][19]

因此，经验研究已经形成的认识不是选出一种通用的最佳载体，而是让对象与复用方式匹配：相似情境保留案例，重复判断提炼规则，稳定子过程封装程序，反复优化保留提案历史。接下来的问题是，当这些对象都已存在，系统能否从反馈中学会更有效地选择、写入和维护它们？下一章讨论记忆管理本身的学习，将改变记忆内容与改变管理过程分开。
