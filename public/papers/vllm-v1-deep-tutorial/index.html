第一部分 · 心智模型、架构与启动

1. 阅读方法与关键纠偏

理解 vLLM V1 最有效的方法，不是从某一个类一路向下追调用栈，而是盯住三个边界：前端到 EngineCore、Scheduler 到 Worker、逻辑 token 到 KV block。每越过一个边界，都问四件事：谁拥有状态、传了什么、没有传什么、完成信号怎样回来。这样读源码，PD、Offloading、并行执行和流式输出都只是同一套骨架上的扩展。

本文面向已经能够启动 vLLM、发送 OpenAI 兼容请求，并希望进一步读懂 V1 源码的读者。建议先熟悉 Transformer 自回归推理、prefill/decode、KV cache、Python async/process 以及基本的 GPU 并行概念。不了解某个高级特性不会妨碍阅读主线；先把一次普通 generate 请求走通，再把 PD、Offloading、MoE 和 speculative decoding 看成主线契约上的扩展。

最小术语表：TTFT 是首 token 延迟，TPOT 是输出 token 间平均延迟；TP/PP/DP/EP 分别表示 tensor、pipeline、data、expert parallelism；PCP/DCP 是两类 context parallelism；DBO 是 dual batch overlap；SSE 是服务端事件流；NIXL 是 PD/远端 KV 数据通道之一。术语只说明切分维度，不能代替实际进程拓扑与 feature gate。

贯穿全文的三个账本
  1. 请求进度账本：num_computed_tokens、输入/输出 token、请求状态；主要由 Scheduler 持有。
  2. 资源账本：请求占有哪些 KV block、哪些 block 可复用或回收；由 KVCacheManager 与 BlockPool 管理。
  3. 执行账本：某个 req_id 在 Worker 的 batch 行、block table、采样状态与 CPU/GPU buffer 中位于哪里；由 ModelRunner 缓存。
三本账通过 SchedulerOutput 与 ModelRunnerOutput 对账，而不是共享一个巨大的可变对象。

2. V1 全景架构：语义、资源与张量三层分工

V1 的核心不是“多了一个 EngineCore 进程”，而是把变化频率不同的工作隔离开：协议和文本语义可以快速迭代，调度与资源状态需要严格一致，GPU 热路径则追求稳定形状与最少 Python 开销。三层通过窄接口连接。

2.1 两条控制链和一条数据事实

前端 ↔ EngineCore 是请求级消息接口。多进程服务中，AsyncMPClient 通过 ZMQ ROUTER/PULL 发送 EngineCoreRequest、接收批量 EngineCoreOutputs。它的重点是隔离协议处理和引擎循环，而不是把每个 token 都包装成一次同步 RPC。

EngineCore ↔ Worker 是 step 级执行接口。Scheduler 每轮产出一个面向整批请求的 SchedulerOutput；Executor 将同一条执行命令广播到模型并行 Worker。Worker 返回 ModelRunnerOutput，Scheduler 再据此推进请求、释放资源并产生面向前端的增量输出。

EngineClient 与 EngineCoreClient 为什么分开
serving 依赖高层 EngineClient 抽象：generate/encode/abort、health/profile、cache reset、sleep/wake、添加 LoRA 与 pause/resume 等能力都可通过同一接口调用；AsyncLLM 是主要实现。它内部再持有低层 EngineCoreClient：当前前端可发送的 wire 类型完整地包含 ADD、ABORT、START_DP_WAVE 与 UTILITY 四类；profile、cache reset、sleep/wake、LoRA、collective RPC 等运维调用通常封装为 UTILITY，而 START_DP_WAVE 服务于 DP wave 协调。这样 HTTP serving 不必知道 EngineCore 是 in-process、multiprocess 还是 DP client，也不会把运维能力塞进生成请求对象。

EngineCore “有多少模块”没有稳定的唯一数字。 若按当前实例字段和责任分组，可读成：Executor/Worker 编排、KV cache 初始化与配置、Scheduler 及其 managers、structured-output 管理、connector 握手/metadata、batch/abort 队列与辅助 hasher/cache 六组；若把每个 manager、queue 或启动期对象分别计数，数字会立刻变化。教程因此按职责和跨层 contract 讲解，而不把“7 个模块”等临时计数写成架构定律。

2.2 为什么不同模型和协议能共用 EngineCoreRequest

EngineCoreRequest 不是 OpenAI 请求的镜像，而是“进入调度器后仍然必要的信息”的规范化表示。chat message、completion prompt、不同 tool schema 等协议差异先在前端被 renderer、chat template 和 tokenizer 消化；EngineCore 看到的是 token、采样/池化参数、多模态特征引用、LoRA、优先级和少量扩展状态。

2.3 Frontend ↔ EngineCore 的 wire protocol 与 DP 路由

多进程模式使用两条方向相反的 ZMQ 通道。前端在输入侧绑定 ROUTER，每个 EngineCore 以自己的 identity 连接 DEALER；EngineCore 的输出侧使用 PUSH，前端以 PULL 汇集批量结果。输入帧的逻辑布局是 (engine_identity, request_type_byte, *msgpack_frames)，其中请求类型可为 ADD、ABORT、START_DP_WAVE 或 UTILITY。大 CPU tensor/ndarray 可作为 out-of-band frame 发送，但这不表示后续 H2D 也零拷贝。

在 DP 内部负载均衡模式中，一个 DPLBAsyncMPClient 同时管理多个 EngineCore identity。当前 identity 是 DP rank 的两字节 little-endian 表示；路由器综合 waiting/running 数、KV 使用率和本前端的 in-flight 计数选择目标，并记录 request_id → engine identity，使 abort 能回到原 EngineCore。外部负载均衡模式则由上游先选定 rank，client 不再自行跨 rank 选择。

wire 上的三个例外
DEALER 收到输入时，ROUTER identity 已被 ZMQ 路由层剥离，它只解码 type 与 payload；启动 READY 是不带 request-type tag 的 EngineCoreReadyResponse；故障通知则是输出通道的单帧 ENGINE_CORE_DEAD。当前枚举中的 EXECUTOR_FAILED、WAKEUP 是 EngineCore 内部队列 sentinel，不应画成前端可发送的业务请求。
为什么一个请求类型不能承载所有未来特性？
共享 EngineCoreRequest 不是拒绝扩展，而是把扩展分层：协议差异先降为 SamplingParams/PoolingParams、多模态 feature spec 和启动配置；只在核心确实需要新语义时追加 optional 字段。该结构使用 array_like 与 omit_defaults，新增字段应追加在末尾并给默认值；管理型能力则走 UTILITY，避免把所有控制命令都塞进生成请求。

3. 模型、权重与 KV 内存如何加载

启动顺序很重要：vLLM 必须先知道模型分片真实占了多少显存，才能把剩余预算切成 KV blocks。因此“权重加载”和“KV cache 分配”不是同一个动作，也不能用一个固定百分比预先分家。

3.1 从 EngineCore 到每张 GPU 的权重

  1. AsyncLLM 根据 VllmConfig 选择 Executor，并由 EngineCoreClient 启动后台 EngineCore。
  2. EngineCore.__init__() 先构造 executor_class(vllm_config)。多进程后端为每个模型并行 rank 拉起一个 WorkerProc。
  3. 每个 Worker 绑定自己的 device，初始化分布式组与 NCCL buffer，清理 allocator 后记录启动显存快照。
  4. Worker.load_model() 调用 GPUModelRunner.load_model()；后者根据 LoadConfig 选择 model loader，再由模型实现按 TP/PP 等配置实例化本 rank 的权重分片。

所以并不是 EngineCore 先加载一个完整 nn.Module 再“发给”各 GPU。模型对象和权重从一开始就在 Worker 进程内创建；EngineCore 只持有配置、调度状态和 Executor 代理。

权重文件究竟来自哪里？

默认 loader 先判断 model 是否是本地目录；若不是，可按配置从 Hugging Face Hub 下载，也可由 ModelScope 适配先解析成本地快照。相同节点上的多个 Worker 都会进入 loader，但下载路径由文件锁和共享 cache 协调，不能简单描述成“每张卡各下载一份”。随后每个 rank 按模型实现和 TP/PP/EP 配置装载自己的参数；普通 checkpoint 可能先读一个 tensor 再按 rank 切片，sharded checkpoint 或专用 loader 则可直接读取 rank-local shard。

多节点部署的必要条件是：每个节点都能解析同一个模型标识，或本地绝对路径在每个节点上都存在且内容一致。共享文件系统、预分发到同路径、每节点独立 Hub cache 都可行；只在 driver 节点存在的本地目录不会被 Ray 自动变成远端可读的权重仓库。Ray 的 actor RPC 负责调用方法和放置进程，不会在正常 load_model 热路径中把整个 checkpoint 从 driver 发送给 Worker。

3.2 KV 容量不是权重的固定补集

对每个 Worker rank \(r\)，当前快照的容量决策可写成下列分支。所有 \(M\) 与 \(H\) 的单位均为 byte：

\[ \begin{aligned} M_{\mathrm{req}}^{(r)} &= \left\lceil u_{\mathrm{gpu}}M_{\mathrm{total}}^{(r)}\right\rceil,\\ M_{\mathrm{KV,preMM}}^{(r)} &= \begin{cases} M_{\mathrm{KV,user}}, & \text{manual KV budget},\\ M_{\mathrm{req}}^{(r)}-M_{\mathrm{consumed}}^{(r)} -H_{\mathrm{transient}}^{(r)} -\delta_{\mathrm{CG}}\widehat M_{\mathrm{CG}}^{(r)}, & \text{automatic profiling}, \end{cases}\\ M_{\mathrm{KV}}^{(r)} &=M_{\mathrm{KV,preMM}}^{(r)}-M_{\mathrm{MM,res}}^{(r)} . \end{aligned} \]

consumed 与瞬时 headroom 来自 profile；\(\delta_{\mathrm{CG}}\in\{0,1\}\) 表示是否把 CUDA Graph 估计纳入预算；\(M_{\mathrm{MM,res}}\) 是多模态 IPC 等额外预留。显式设置 kv_cache_memory_bytes 会绕过自动 KV 容量推导，但仍执行 profile run 以完成编译。随后还要按 bytes/block 计算各 rank 的 block 数并取共同可承受的最小值。

不要把 0.92 读成“KV 占 92%”
gpu_memory_utilization=0.92 是本 vLLM 实例希望使用的设备总显存上限，不是 KV 比例。权重大小由模型、量化、TP/PP 决定；激活峰值由 batch、token 数、算子与图捕获决定；KV 才使用预算中的剩余部分。若显式设置 kv_cache_memory_bytes，它会绕过自动 KV 大小决策，但仍需 profile/编译相关过程。

3.3 KV tensor 的实际创建

EngineCore 先从 Worker 获取每层 KVCacheSpec，解析 cache group 与 layout，再生成 KVCacheConfig。Worker 的 initialize_from_config() 最终调用 ModelRunner：分配 backing storage、为各 attention 层建立 view、绑定到 forward context，并把 cache 注册给需要的数据搬运 connector。之后才进行 compile、CUDA Graph capture 或 warmup。

“一大块连续显存”在实现上通常表现为 Worker 内的一块 backing allocation 加多个 layer view，但这不等于请求拥有连续 block，也不等于 CUDA 物理页连续。请求只持有 block ID 序列，任意空闲 block 都可被接到它的逻辑序列后面。

4. 一次请求的端到端旅程

4.1 入站：从协议对象到内部 Request

  1. OpenAI handler 校验请求，并通过 renderer/chat template 把 messages、图片等转换为统一的引擎输入。
  2. AsyncLLM.add_request() 调用 InputProcessor，产生 EngineCoreRequest。原始 prompt 需要 tokenize 或多模态处理时会放到异步路径，避免阻塞事件循环。
  3. 前端先在 OutputProcessor 中创建 RequestState 和该请求的 collector，再调用 engine_core.add_request_async()。先登记输出状态可以避免引擎极快返回时找不到接收者。
  4. AsyncMPClient 编码请求并经 input socket 发给目标 EngineCore。EngineCore 侧将消息放入 input queue，preprocess_add_request() 把它转换成内部 Request，最后进入 Scheduler 的 waiting queue。
普通 OpenAI 请求会走 StreamingInput 吗？
通常不会。常规 Chat/Completion 请求先由 renderer 与 InputProcessor 产生已经规范化的 EngineInput；只有调用方把 prompt 本身提供为 AsyncGenerator[StreamingInput] 时，AsyncLLM 才进入 streaming-input session，随后用相同 request ID 追加输入 chunk。该路径已经有实现和测试，但当前对 pooling、n>1、stop strings 等组合存在限制，不能把它理解成所有请求的新默认入口。

4.2 核心循环：同步闭环与异步流水

当前提交有两条核心路径。配置兼容时，async_scheduling 会自动启用，因此不能再把严格 ping-pong 写成默认事实。非队列路径仍是理解契约的最短骨架，但它也包含 grammar bitmask 与可独立执行的 sampling：

# 同步兼容路径（删去统计与错误处理）
scheduler_output = scheduler.schedule()
future = model_executor.execute_model(scheduler_output, non_block=True)
grammar_output = scheduler.get_grammar_bitmask(scheduler_output)
model_output = future.result()
if model_output is None:
    model_output = model_executor.sample_tokens(grammar_output)
process_aborts_that_arrived_during_execution()
engine_outputs = scheduler.update_from_output(scheduler_output, model_output)

schedule() 是“预提交”：它为本 step 选择 token、分配 block，并将进度标为在途；update_from_output() 是“提交/校正”：接收采样结果、处理 spec rejection/停止条件、释放结束请求，并形成面向单请求的 EngineCoreOutput。普通生成路径携带 token 级增量及相关元数据（如 logprobs、finish/stop reason、事件和 connector 参数），不携带前端累计后的完整文本；pooling 路径还可携带 Tensor 输出。

EngineCoreOutputs 是一次回程消息的容器，其 outputs: list[EngineCoreOutput] 可以为空。Scheduler.update_from_output() 只有在 new_token_ids 非空、存在 pooler_output 或请求停止时才为该请求追加条目；纯 partial/chunked prefill 因而不产生该请求的 EngineCoreOutput。反过来，结束/错误条目可以携带空的 new_token_ids。容器还可只承载 scheduler_stats、finished_requests、utility_output 或 DP wave 信号，所以“一个 step 必有一条请求输出”与“容器为空就无意义”都不成立。

异步路径使用 step_with_batch_queue()。经典 runner 在 PP≤1 且 async 开启时通常允许 2 个并发 batch；MRV2 的并发上限是 PP+1。它把 forward、grammar 准备和 sampling 组织为 Future，并按提交顺序取回最老结果。若 structured output 仍在等待前一步产生的 token，sampling 会延后到 grammar bitmask 可计算时再进入队列。

准确的统一心智模型
同步和异步路径都遵守 schedule 预提交 → execute/sample → update 校正。区别只是允许多少批次同时在途，以及 sampling 是否与 forward 解耦；不是两套 Scheduler，也不是 Worker 自己决定下一批请求。

4.3 出站：token ID 在哪里变回文本

  1. EngineCoreProc 在需要回传时把一个 EngineCoreOutputs 容器写到 output socket；其中请求条目 outputs 可为 0…N 条。
  2. AsyncMPClient 的 socket-receive task 解码 EngineCoreOutputs；utility 结果在 client 内兑现对应 future，生成输出/统计则放入 asyncio queue。
  3. AsyncLLM._run_output_handler() 持续拉取批量输出，并分块交给 OutputProcessor.process_outputs()，避免一次处理过多请求而长期占据 event loop。
  4. OutputProcessor 根据每个请求自己的增量 detokenizer、logprobs 与输出模式更新 RequestOutput，再推入 per-request collector。
  5. AsyncLLM.generate() 从 collector 取出一个前端已组装好的 RequestOutput 并 yield；API 层再生成 text/tool/reasoning delta 与 SSE。

_run_output_handler() 是幂等启动器：若构造时已有 event loop 会提前创建 task，否则普通或 streaming add-request 路径会启动它；self.output_handler is not None 的 guard 保证每个 AsyncLLM 只有一个常驻回收 task，而不是每个请求新建一个。这里字段 AsyncLLM.output_handler 保存的是 asyncio.Task，嵌套的 output_handler() 异步函数及其循环才是 coroutine。UTILITY 调用不会调用 AsyncLLM._run_output_handler()；但 AsyncMPClient._call_utility_async() 会确保另一项 resources.output_queue_task 已启动，以便 socket 接收协程兑现 utility future。两项 task 不应混称为同一个“output handler 协程”。

关键纠偏
EngineCore 输出的是增量 new_token_ids，不是已经 detokenize 的字符串。detokenization 位于前端 OutputProcessor；一次 async for 迭代表示前端发出一个 RequestOutput，不保证严格对应“一个 GPU step”或“一个 token”。队列聚合、spec decode 和 stream_interval 都可能改变粒度。

5. EngineCore 与 Scheduler：把不同阶段统一成 token 差额

Scheduler 的目标不是识别“这是 prefill 请求还是 decode 请求”，而是在 token budget、并发上限、KV 容量、encoder budget、结构化输出等约束下，决定每个请求本轮推进多少。prefill/decode 是由进度差自然呈现出来的工作形态。

5.1 一个统一的进度方程

\[ N_{\mathrm{pending}} \approx N_{\mathrm{tokens+spec}}+N_{\mathrm{output\ placeholders}} -N_{\mathrm{computed}} . \]

新请求的已计算值通常为 0，差额可能是数百或数千，于是本轮调度一个 prompt chunk；完成 prompt 后，普通自回归请求每得到一个新 token，下一轮差额通常又变成 1，于是表现为 decode。prefix cache 会把起点前移，spec decode 会让差额大于 1，chunked prefill 会受 token budget 截断——都不需要再维护一个独立的 phase 状态机。

5.2 调度顺序与物理上限

  1. 先看 running：按请求当前差额、长 prefill 阈值、全局 token/input budget、最大长度等裁剪 num_new_tokens。
  2. 申请 KV slot：KVCacheManager.allocate_slots() 计算要新增多少 block，并检查 free blocks、可驱逐 prefix block、watermark 等。若无法满足，Scheduler 会选择低优先级/队尾 running 请求抢占；没有可抢占对象时，本轮停止继续装载。
  3. 再接纳 waiting：先查本地 prefix cache，再让可选 connector 查询外部 KV；随后检查 max_num_seqs、LoRA、encoder cache、token budget 和 KV 容量。
  4. 构造 step 契约：生成 num_scheduled_tokens、new/cached request 数据、block 差量、结束请求集合及 connector metadata。

所以 Scheduler 判断“物理上限”不是拿一个固定 token 数作比较，而是让 cache manager 按当前 block pool 状态实际尝试分配。长上下文 decode 的压力主要体现在长期占用越来越多的 KV blocks 与 max_num_seqs；同样 16k token，prefill 更偏计算吞吐，带 16k 历史的并发 decode 更容易先撞到常驻 KV 容量。

5.3 new 与 cached 是传输优化，不是计算阶段

5.4 为什么 schedule 后先推进 num_computed_tokens

Scheduler 在发出 SchedulerOutput 后就把本轮 token 标成 in-flight，使 batch queue 路径可以继续调度后续 batch；模型结果回来时再根据 spec rejection、失败或抢占校正。这是一种带回滚的预提交。读异步调度源码时，如果忽略 num_in_flight_tokens，很容易误以为请求已经“完成了尚未执行的 token”。

5.5 公平性、skipped_waiting 与 pending cache

FCFS 在 V1 中是有序但 work-conserving，不是“队头暂时不可运行就让整张 GPU 空转”的绝对严格 FCFS。waiting 请求若处于远端 KV/grammar/streaming 等阻塞状态，connector 暂时返回无法判定（例如 offload 的 HIT_PENDING/RETRY 语义），或因 LoRA、stale output 等本 step 约束不能接纳，会被移入本 step 的 step_skipped_waiting；调度器继续检查后面的 ready/MISS 请求，避免 head-of-line blocking。

本 step 结束时，暂存请求按原有次序 prepend 回持久的 skipped_waiting。下一 step：FCFS 先检查 skipped 队列，再看普通 waiting；PRIORITY 则比较两个队列的队头。因此 pending 请求会持续被重查，但不会垄断本轮算力。这解释了“有 cache 的请求反而晚于无 cache 请求”的可能性：它是为吞吐和避免空转做的有界绕行，不是 cache 查询顺序丢失。抢占后 num_computed_tokens 可重置为 0，请求也可能再次做 prefix/connector lookup，所以“每个请求生命周期只查一次 cache”并不成立。

5.6 RequestStatus：阻塞、运行、抢占与结束

RequestStatus 不是简单的 WAITING→RUNNING→FINISHED 直线。结构化 grammar 编译、远端 KV 接收和 streaming input 都会让请求停在专门的 blocked waiting 状态；抢占会释放本地资源、重置已计算进度并把请求放回 waiting queue。只有枚举中位于 PREEMPTED 之后的 FINISHED_* 才满足 is_finished()。

5.7 client disconnect 如何反向释放资源

  1. 客户端断开、生成协程取消或前端 stop 检查触发 AsyncLLM.abort()；OutputProcessor 先停止该请求的前端 collector，再向原 EngineCore 发送 ABORT。
  2. EngineCore 将执行期间到达的 abort 放入队列，并在处理模型输出前批量调用 Scheduler.finish_requests(..., FINISHED_ABORTED)，避免迟到输出重新推进已取消请求。
  3. Scheduler 从 running/waiting 队列移除请求，调用 connector 的 request_finished hook，释放 encoder cache 与 KV blocks；远端 KV 仍在传输时可以延迟最终 free。
  4. finished_req_ids 随后进入 SchedulerOutput。经典 runner 删除 CachedRequestState 和 InputBatch 行；MRV2 释放 permanent row 及相关 GPU/CPU 状态。迟到的前端输出按 request ID 丢弃。
abort 与抢占不同
abort 进入 FINISHED_ABORTED，生命周期结束；preemption 使用 PREEMPTED，请求仍保留在 Scheduler 中等待恢复。二者都可能让 Worker 清理旧执行状态，但只有后者预期重新加入 batch。

6. KV Cache、block table 与显存：从 token 位置到本地存储槽

Paged KV 的关键不是“把显存切成小块”这句口号，而是把请求的逻辑序列位置与 Worker 的KV pool 位置解耦。请求可以逐步追加任意空闲 block，prefix 相同的请求可以安全共享只读 block，抢占时也能按引用计数释放。

6.1 block_id 到底“物理”到什么程度

KVCacheBlock.block_id 的取值范围是 0 … num_gpu_blocks-1，因此它可称为 vLLM 分配器意义上的“物理 block 号”；但它仍只是软件索引，不是 GPU 虚拟地址、HBM 物理页号或跨机器统一地址。标准 attention 路径可用下式理解逻辑 token 到 pool slot 的映射；混合 cache group、virtual block split、DCP/PCP 与不同 layout 会让映射更复杂。

\[ \begin{aligned} q&=\left\lfloor\frac{t}{b_g}\right\rfloor, &o&=t\bmod b_g,\\ \beta_{i,g}^{(r)}&=\mathcal T_{i,g}^{(r)}[q], &s_{i,g}^{(r)}(t)&=\beta_{i,g}^{(r)}b_g+o . \end{aligned} \]

这里 \(b_g\) 是 cache group \(g\) 的 tokens/block，\(\mathcal T\) 是请求 \(i\) 的 block table，\(s\) 是 rank \(r\) 本地 KV tensor 的逻辑 slot，仍不是显存地址。多卡时不存在“所有 GPU HBM 统一编号”：同一个 block_id=7 在各 TP/PP rank 上选择各自 cache 中的第 7 个调度 block，承载的是该 rank 负责的 head/layer 分片。跨实例搬运还必须携带 engine、rank 与 layout 上下文。

数字化例子：token 6 为什么落到 slot 10

令 block size \(b=4\)，请求的 block table 为 [7, 2, 11]，token 位置按 0 开始编号。对 t=6：

\[ q=\lfloor 6/4\rfloor=1,\qquad o=6\bmod 4=2,\qquad \beta=\mathcal T[1]=2,\qquad s=2\times4+2=10. \]

所以 token 6 属于请求的第 1 个逻辑 block，使用 pool block 2 的第 2 个偏移，对应逻辑 slot 10。这里的 10 仍需由具体 KV layout 转换成 tensor view/stride；它不是 CUDA 地址。

6.2 为什么不同请求不会互相污染

  1. Scheduler 的 block pool 为新尾部选择空闲 block，并增加引用计数；请求只在自己的 block table 行中引用它们。
  2. Worker 按 req_id 找到 batch 行，再由该行 block table 生成本轮 token 的 slot mapping，attention kernel 只读写这些 slot。
  3. 默认 Transformer/full-block 路径只共享内容哈希相同、已经计算完成的前缀 block；需要继续写入的尾部使用私有 block。当前部分 hybrid Mamba align 配置还支持 hash-block 粒度的 partial hit：Worker 先把共享尾部复制到私有 copy-on-write block，再继续写入。
  4. 请求结束后释放引用；引用降为 0 的 cached block 可留作 prefix 命中候选，也可按淘汰顺序重新分配。

6.3 从显存字节到 block 数

KVCacheSpec 描述每类层的 dtype、heads、head size、block size 与 layout。令 \(P_\ell^{(r)}\) 为 rank \(r\) 上层 \(\ell\) 的 page_size_bytes（已包含 layout padding），则 cache groups 共享同一 allocation 起点，容量取最宽 group，而不是把所有 group 再次相加：

\[ \begin{aligned} C_{\mathrm{blk}}^{(r)} &=\max_{g\in\mathcal G_r}\sum_{\ell\in g}P_\ell^{(r)},\\ \widetilde N_r &=\left\lfloor\frac{M_{\mathrm{KV}}^{(r)}}{C_{\mathrm{blk}}^{(r)}}\right\rfloor,\\ N_{\mathrm{blocks}} &=\min_r\widetilde N_r, &N_{\mathrm{usable}}&=N_{\mathrm{blocks}}-1 . \end{aligned} \]

BlockPool 永久保留 block_id=0 作为 null block，因此可分配给普通请求的数量要减一。num_gpu_blocks_override 则直接覆盖自动推导值，配置过大可能 OOM。这也解释了为什么相同 GPU 上，不同模型、KV dtype、TP 大小、MLA/MHA、滑窗或混合 Mamba cache 会得到不同容量。对 B200 一类设备也应按实际 SKU 与当前进程实测，不假定唯一显存规格。

6.4 prefix 命中为何仍重算最后一个 token

要采样下一个 token，需要最后一个位置的 logits。若 prompt 全部从 KV 命中而没有 forward，就没有这次请求所需的 logits。因此 cache manager 会把最大命中长度限制在 prompt 末尾之前，让最后一个 token（受 block 对齐影响时可能是最后一个 block）重新计算。这不是 cache 失效，而是“KV 可复用”和“必须产生 logits”两个目标的交点。

纠偏：block table 不是地址表
把它理解为“每个请求的逻辑页号 → vLLM pool block 号”是对的；把右侧值继续等同于 HBM 地址则不对。真正的 tensor view、stride、layout 和 slot mapping 都在 Worker 内完成，EngineCore 不需要也不应持有 CUDA pointer。

6.5 prefix hash chain、命中与多租户 cache_salt

prefix cache 的 key 不是“只对当前 block token 做一次 hash”。每个 hash 都包含 parent hash、当前 token IDs 以及 LoRA、多模态等额外 key，因而形成从前缀起点向后的 hash chain。通常命中沿 Scheduler block 边界连续延伸；当前提交仅在满足 feature gate 的 hybrid Mamba align 配置中允许更细的 hash-block 边界命中，并用私有 CoW block 承接后续写入。引用计数为 0 的 cached block 可留在 pool 中等待复用，空闲 block 不足时再按淘汰策略重新分配。

多租户 prefix cache 必须显式划分信任域

cache_salt 只加入第一个 block 的 hash，但后续 block hash 包含 parent hash，所以整条 chain 都随 salt 改变。同一 salt、相同前缀仍可复用；不同 salt 即使 token 完全相同也不会互相命中。

它不是加密、认证或显存访问控制。多租户部署应使用不可预测的随机 secret，并按用户、租户或允许共享 cache 的组织边界设置；无 salt 会保留跨请求共享，只适合单租户或不关心 prefix timing side channel 的环境。隔离粒度越细，跨请求命中率越低。

7. Executor、Worker 与 ModelRunner：如何把调度指令变成一次 GPU 执行

三者经常被混称为“执行层”，但职责不同：Executor 管进程/远端 actor 和 collective RPC；Worker 管一张设备及分布式环境；ModelRunner 管模型、请求状态、batch buffer、attention metadata、forward 与 sampling。当前提交同时存在经典 GPU ModelRunner 与 MRV2，两者遵循同一个 SchedulerOutput/ModelRunnerOutput 外部契约，但内部状态布局不同。

Executor：编排者

把方法调用广播到所有模型并行 ranks，选择返回 rank，处理 Future、超时、进程死亡和可选的 connector 输出聚合。它不构造 attention tensor。

Worker：设备所有者

绑定 local rank/device，初始化通信组，加载本 rank 权重，profile 显存，创建 KV cache，并把 execute_model 转交 ModelRunner。

ModelRunner：热路径

接收 new/cached 差量，准备 input/position/block table/slot mapping，运行模型并采样。经典路径依赖 CachedRequestState；MRV2 使用 permanent row 与 GPU-native 状态。

Attention backend：内核契约

消费 attention metadata、block table/slot mapping 与 KV view，在本 rank 上完成读写；不同 backend 可有不同 kernel block size。

7.1 一次 collective RPC 怎样往返

MultiprocExecutor.execute_model() 调用 collective_rpc("execute_model", ...)，把方法名和同一个 SchedulerOutput 放入广播队列。每个 Worker 主循环取出命令并调用本地 Worker/ModelRunner。若使用 PP，前级输出的 intermediate tensors 在 Worker 的 pipeline 通信路径中流向后级；它们不会绕回 EngineCore。

普通生成通常只需最后 PP stage 对应的 output_rank 返回采样结果。若 KV/EC connector 必须收集每个 rank 的传输完成状态，Executor 会把 output_rank 设为“收全部”，再用 aggregator 合并到一个 ModelRunnerOutput。因此 future.result() 对 Scheduler 仍返回一个逻辑结果，但其来源取决于是否启用聚合器。

7.2 Worker 如何凭 req_id 找回上下文：Classic 与 MRV2

经典 GPU ModelRunner 维护 requests: dict[str, CachedRequestState]，并在 InputBatch 中保存 req_id → batch index、token buffer、已计算长度、采样参数和每组 block table。请求加入/结束时可能移动 persistent batch 的行，因此需要一份 Python 侧请求状态作为备份。

7.6 Speculative decoding：为什么一个 step 会返回多个 token

spec decode 不是普通 decode 后再“多猜几个字符串”，而是跨 step 的候选—验证循环。N-gram、suffix、EAGLE/MTP 或独立 draft model 产生候选的方式不同，但 target 验证和 Scheduler 校正遵循共同契约：

\[ a_j=\min\!\left(1,\frac{p_{\mathrm{target}}(z_j)}{q_{\mathrm{draft}}(z_j)}\right) \]

上式描述带 draft probability 的标准随机 rejection sampling；greedy 路径比较 draft token 与 target argmax。若全部候选被接受，target 可再产生 bonus token；若中途拒绝，则在首个拒绝位置采 correction token。一步因此可以提交 \(1\ldots k+1\) 个有效 token。Scheduler 预提交时把 drafts 算入 num_tokens_with_spec，结果回来后按 accepted/rejected 数回滚进度；被拒绝后缀不再成为已提交上下文，但不能简单声称其 KV 字节一定立刻清零。

7.7 IPC、Tensor 与“零拷贝”的边界

单机 multiprocessing 的 MessageQueue 为本地 reader 配置共享内存 ring，但较大 out-of-band buffer 可走 socket，远端 reader 则走 TCP/ZMQ。序列化器会对 CPU tensor 做专门 reduction；前端 ↔ EngineCore 的多模态配置还可使用 tensor IPC queue。它们是在减少复制和 pickle 开销，而不是承诺任意对象、任意拓扑都零拷贝。

更重要的是，CPU IPC buffer 与 GPU 模型输入不是同一块存储。ModelRunner 通常仍要把 token/metadata 写入 pinned CPU buffer 并 H2D；模型权重、激活和 KV 从不通过这个控制队列逐 step 传输。对于 prompt_embeds 或多模态 tensor，应按所选 IPC 后端讨论具体复制链，不能用“EngineCore 只有 list[int]”一概而论。

PP 场景的准确表述
EngineCore 的一次 step 仍对应一次面向全部 Worker 的执行命令；不是 EngineCore 对每个 PP stage 依次调用多次 ModelRunner。各 stage 在同一 collective RPC 下执行自己的分片并进行 stage 间通信。batch queue、PP microbatch 或 async scheduling 可以让多个 batch 在途，但这是执行流水线深度，不是把一个 step 改写成多次前端调度。

8. 从 token ID 到 SSE：Detokenizer、Parser 与多对多流式关系

关键纠偏
EngineCore 输出的是 token ID、finish reason、logprobs/统计和 connector 参数等增量结构；detokenization 位于前端进程的 AsyncLLM / OutputProcessor，不在 EngineCore 内。这样 GPU 调度核心无需持有 tokenizer 和每个客户端的文本状态。

§7.5 的 structured outputs 在采样前限制允许 token；本章的 Parser 在生成后解释这些 token。二者可能由同一个 tool-call 请求串联，但不能互换。

8.1 OutputProcessor：批量回收、逐请求处理

AsyncLLM.output_handler 字段保存常驻 asyncio.Task，不是 coroutine 对象；AsyncLLM._run_output_handler() 内部定义的 async def output_handler() 及其循环才是 coroutine。该 task 批量从 EngineCore 拉取 EngineCoreOutputs，按 VLLM_V1_OUTPUT_PROC_CHUNK_SIZE 切块，块间 await asyncio.sleep(0) 让出事件循环。它由已有 event loop、普通/streaming add-request 路径幂等启动，不由 UTILITY 调用启动；UTILITY 只会确保更低层的 AsyncMPClient.resources.output_queue_task 在收 socket 回包。process_outputs() 是系统中有意保留的那一次“遍历完整请求输出批”：

  1. 按 request_id 找前端 RequestState；已 abort 的迟到输出直接丢弃。
  2. 增量 Detokenizer 将 new_token_ids 变成文本，并检查 stop string。若前端先发现停止条件，会把 request ID 反向 abort 给 EngineCore。
  3. 更新 logprobs、prefill/spec-decode 指标，构造 RequestOutput。
  4. 异步路径把结果放入该请求的 RequestOutputCollector；同步 LLMEngine 路径才把列表作为返回值交给调用者。

不同模型的 token→text 细节确实不同：tokenizer vocab/special tokens、byte fallback、fast/slow incremental backend 和 chat template 都会影响边界。vLLM 的统一点不是“所有模型共享同一转换规则”，而是把差异封装进 tokenizer 与 per-request incremental detokenizer，使 OutputProcessor 仍能使用稳定接口。

pooling 请求为何不走同一条 token→text 链

pooling runner 产生 embedding、classification、score 等 pooler_output，而不是下一 token logits；Scheduler 可在 EngineCoreOutput 中携带 tensor 结果，前端再按 endpoint/task 封装为对应响应。因此 pooling 与 generate 共享请求、调度和 Worker 外壳，但不经过自回归 sampler、增量 detokenizer 或 SSE token delta。

8.3 Parser：模型语法驱动的增量状态机

Chat serving 为每个 choice 建独立 parser，并调用 parse_delta(delta_text, delta_token_ids, finished)。普通 DelegatingParser 先处理 reasoning 边界，再把正文交给模型专属 ToolParser。ToolParser 不是凭语义“猜”工具调用，而是理解对应模型约定的特殊 token、XML/标签或 JSON 包装：

  • 普通文本可立即成为 DeltaMessage.content。
  • 疑似半个工具标签或未成形 JSON 时返回 None，serving 暂不发该语义 chunk，等待后续 token。
  • 工具名通常只发一次；arguments 维护已发送前缀，只发新增后缀，客户端按 tool index 拼接。
  • parser 没有语义 delta 时，当前 serving 通常跳过该帧；但若请求结束，或 return_token_ids=True 且 reasoning 未被隐藏，它会当场构造空 DeltaMessage，用来保留 finish/token IDs。原因是当前实现没有“被 parser 抑制 ID 的待发缓冲区”；这不是协议层理论上不能延后。

为什么新版采用 DSML：可证事实与工程解释的边界
模型侧的可证事实是 checkpoint/chat template 约定输出 DSML，serving 必须按该协议解析；vLLM 侧的选择则是用声明式 ParserEngineConfig 实现它，而不是继续为每代语法复制计数器与正则。由实现可直接观察到的工程收益包括：显式 wrapper/invoke/parameter 边界可映射为确定的状态转移；特殊 token 与增量 lexer 能处理标记跨 chunk；string=true/false 让参数转换器区分原样字符串与需要 json.loads 的数值/布尔/对象；TOOL_BETWEEN 明确支持并行调用；V4 还能在同一状态机中连接 REASONING、CONTENT 与 TOOL 状态。这些是源码呈现的性质与合理工程解释，不等同于 DeepSeek 官方声明的产品决策原因。
GPT-OSS 走 Harmony，不走 DeepSeek 的 ParserEngine
GPT-OSS 的结构化解析实现是 HarmonyParser：启用相应 reasoning/tool 解析时，serving 以模型类型 gpt_oss 设置 is_harmony，由 ParserManager 返回 Harmony 路径。它逐 token ID 驱动 openai_harmony.StreamableParser，根据 channel 与 recipient 产出 reasoning、正文或 tool delta；GptOssReasoningParser 与 GptOssToolParser 主要是能力声明/边界接口。把 GPT-OSS 归到 DeepSeek DSML 状态机是不准确的。

8.4 SSE 收尾

Parser 产出的 DeltaMessage 被包装成 ChatCompletionStreamResponse，序列化后以 data: {json}\n\n yield。每个 choice 的 finish reason 只发送一次；若开启 usage，还会追加 choices 为空的 usage chunk；最后发送 data: [DONE]\n\n。SSE frame 是应用层边界，底层 TCP 仍可能合并或拆分网络包。

9. TP、PP、DP 与 Ray：并行维度和执行后端不是一回事

理解 vLLM 的并行，先把两类问题拆开：TP / PP / DP 决定模型与请求如何分工；mp / ray / external_launcher 决定这些 Worker 进程如何被拉起、放置和控制。Ray 不是第四种模型并行，TP 也不是一种进程启动器。

9.1 TP：SPMD 下发一次，集合通信在模型代码内发生

EngineCore 不会逐个指挥“rank 0 先算这一层、rank 1 再做 all-reduce”。Executor 把同一份 SchedulerOutput 广播给各 Worker；每个 Worker 走相同的模型控制流，分片线性层或 attention 层在执行到相同位置时自行触发 NCCL 集合通信。正确性依赖所有参与 rank 的调用顺序一致，因此某个 rank 提前跳过 collective 会让其他 rank 永久等待。

为什么通常只收一个 rank 的结果？
TP/PP 下最终可采样的 logits 只在特定输出 rank（通常是最后一个 PP stage 中的相应 rank）有意义。MultiprocExecutor.execute_model() 因而以 unique_reply_rank=self.output_rank 回收普通模型输出；但 KV/EC connector 的完成状态可能来自多个 rank，此时会先由 aggregator 汇总，不能把“只收输出 rank”误读成“其余 rank 从未返回任何状态”。

QKV 与 O projection 的 worked example

设 dense MHA 的 hidden size (H=8192)、64 heads、head dim 128、TP=4。典型 QKVParallelLinear 沿输出/head 维切分：每 rank 负责 16 个 Q/K/V heads，本地 fused QKV 输出宽度为 (3H/4=6144)，attention 本地输出宽度为 (H/4=2048)。随后 RowParallelLinear 沿输入维持有 O projection 的 (H/4) 分片，每 rank 产生形状 ([T,H]) 的 partial output，最后 all-reduce 合并。

ColumnParallelLinear.weight_loader 默认沿 output_dim 截取本 rank shard，RowParallelLinear.weight_loader 默认沿 input_dim 截取；QKVParallelLinear 还处理 GQA 下 KV-head replication。若参数已标记为 sharded weight，或使用 rank-local/sharded loader，Worker 可直接读取本地 shard，不能概括成“每个 Worker 总先读完整权重再切”。

9.2 PP：不仅切权重，还要隐藏 pipeline bubble

非首 stage 先通过 irecv_tensor_dict 接收上一 stage 的中间张量，运行本 stage 后，非末 stage 用 isend_tensor_dict 发给下一 stage。单批严格串行会留下流水线空洞，因此 EngineCore 可启用 batch_queue：先让多个批次的异步 Future 在 pipeline 中飞行，再按顺序取回完成结果。它改变的是批次重叠方式，不改变 Scheduler 对请求 token 和 KV block 的账本。

9.3 DP：dense/non-EP 下是完整副本；与 PD 完全正交

对 dense 模型或未启用 expert parallelism 的部署，DP 的每个副本都能执行完整的 prefill 和 decode，通常由负载均衡层把不同请求送到不同副本。启用 DP+EP 后不能再把所有参数理解为完全独立复制：attention 等 dense 路径仍按各 DP batch 工作，而 expert weights 与 token dispatch/combine 可跨 TP×PCP×DP ranks 组织。PD 则把同一个请求的 prefill 与 decode 依次交给两类实例。二者可以叠加：P 侧有 X 个 DP 副本，D 侧有 Y 个 DP 副本，即常说的 XpYd；不能把 PD 叫作一种 DP。

MoE 的 DP+EP 场景还有一个容易忽略的同步约束：即使某个 DP rank 当前没有真实 token，只要其他 rank 将进入专家 all-to-all，它也必须执行 dummy batch 参与 collective，否则会死锁。这里的“空执行”是通信一致性要求，不是 Scheduler 凭空制造请求。

共享内存 RPC 并不等于“所有对象普遍零拷贝”
本机广播环避免了为每个读者分别走 socket，但消息仍要序列化；普通 Python 对象仍会构造和反序列化。大 CPU tensor 可用 pickle5 out-of-band buffer 避免塞进主 pickle 帧，而共享内存 ring 的块会被 writer 复用，接收侧重建 tensor 时必须 copy-out 才能保证生命周期安全。远端 reader 更要经过 TCP/ZMQ。准确说法是“减少复制、对部分缓冲区提供零拷贝路径”，不是“跨进程调用天然零拷贝”。

10. PD 分离与 NIXL：把计算阶段拆开，把 KV 接起来

Prefill 把许多 prompt token 一次送入模型，通常更偏大 GEMM 和计算吞吐；decode 每个序列每步只有少量新 token，却反复读取历史 KV，更看重显存容量、带宽和尾延迟。混部时，长 prefill 会给正在 decode 的请求制造 TPOT 抖动。PD（prefill-decode disaggregation）让两侧独立扩缩容、设置 TP/PP/批预算和通信后端，再用 KV Connector 把阶段边界接起来。

两条必须分开的轴
PD 决定一个请求先去哪一类实例、再去哪一类实例；DP 决定每一类实例有几个等价副本。 例如 2P3D 表示 P 池两个副本、D 池三个副本，路由器分别做选择。
\[ G_{\mathrm{PD}}=G_{\mathrm P}+G_{\mathrm D}. \]

若 1P1D 两侧都保持与原统一实例相同的 TP/PP/PCP 配置，最直观的对称部署约需要原模型并行 GPU 数的 \(2\times\)。若总 GPU 数固定，则不是“凭空翻倍”，而是把原资源拆给 P/D 两侧，每侧的并行度、KV 容量或副本数随之下降。生产容量还要把各池 DP 数、故障冗余和路由余量计入，不能只看一个 TP 参数。

10.1 NIXL Pull 的完整闭环

  1. 路由到 P。 Proxy 选择一个 prefill 实例，注入本次远端交付的 kv_transfer_params。示例代理把 max_tokens（以及 chat 的 max_completion_tokens）改成 1。
  2. P 正常执行 prefill，并且仍会采样一个 token。 max_tokens=1 不是“只 prefill、不采样”的内部开关；它仍走生成路径并采出一个 token，只是 Proxy 丢弃这段响应，把这次请求当作 KV 准备阶段。教程或性能估算不能把这一步的 sampling 成本写成零。
  3. P 暂时保活 KV block。 请求结束时，NIXL scheduler 侧 request_finished() 返回 delay_free_blocks=True，并产出远端 engine、host/port、request ID、TP size、remote_block_ids、有效 token 数等参数。租约/TTL 防止 D 永远不来时泄漏显存。
  4. 路由到 D。 Proxy 把原始生成请求与 P 的寻址参数交给选中的 D。D 先做本地 prefix-cache 查询，再让 connector 报告还能从远端命中多少 token；需要异步加载时，请求进入 WAITING_FOR_REMOTE_KVS，本步不执行它的模型 forward。
  5. 为 D 分配目标 block。 KVCacheManager 仍先在 D 的本地 pool 中分配物理 block；update_state_after_alloc() 只登记“远端哪些 block → 本地哪些 block”，并不在 Scheduler 进程搬字节。随后 build_connector_meta() 把纯元数据塞进 SchedulerOutput。
  6. D Worker 发起 NIXL READ。 首次连接先经 side channel 交换 NIXL agent metadata、注册信息和兼容性信息；之后 Worker 对已注册内存发异步 READ，把 P 的 KV 直接写入 D 的 paged KV buffer。block_ids 是各自 KV pool 的 block 索引，不是 HBM 裸地址，也不是 GPU 物理页号；Worker 结合本 rank 的 KV tensor 布局把索引翻译成传输描述符。
  7. 按 step 轮询完成。 NIXL 传输不依赖 Python 回调唤醒 Scheduler。Worker 的 get_finished() 在后续 step 轮询句柄；即使本步没有可 forward 的请求，也可走 connector 的 no-forward 路径推进收发。
  8. 全 rank 完成后解冻。 TP/PP 场景各相关 Worker 都可能有自己的传输，Executor 的 KV output aggregator 计数聚合；全部完成后 Scheduler 才把请求移回可运行队列。D 发通知给 P，P 在消费者读完后释放保活 block；超时租约是兜底。

10.3 Pull、Push 与上线检查

Pull 模式由 D 主动 READ P 的 block，P 只需保活并等待读取通知；Push 模式则由 D 先公布目标 block，P 用 WRITE 主动推送。二者的握手与 metadata 不同，但都遵循“Scheduler 记账、Worker 搬数据、完成状态回流”的接口。

  • P/D 使用兼容的模型、tokenizer、KV dtype、KV layout、block 语义和 connector 配置。
  • 为每次传输提供全局可区分的 request/transaction identity，并验证超时、取消与重试路径。
  • 测量 T_KV_transfer，不要只看 P 的 prefill 时间；网络拥塞会直接进入 TTFT。
  • 确认 TP 映射。异构 TP 可由 connector 的 topology/read spec 支持，但不能假设“同一个 block ID 在每个 rank 上含义相同”。
  • 把示例 Proxy 当作协议演示而不是生产路由器；生产还需要背压、健康检查、亲和性、故障恢复和指标。

11. KV Offloading：把 prefix cache 延伸到更慢、更大的层级

Offloading 的目标不是让每个 decode step 都从 CPU 或磁盘流式读取历史 KV。那样 PCIe/网络延迟会直接进入每个 token 的关键路径。它更像多级 prefix cache：已完成的 KV chunk 从 GPU 异步下沉；以后相同前缀命中时，再把整段 chunk 提升回 GPU，以一次搬运换掉一次重复 prefill。

11.1 一次 store：新算出的前缀怎样下沉

  1. Scheduler 根据请求 token 边界和 block hash 找出可卸载 chunk。默认 offload_prompt_only=true，主要保存 prompt/prefill KV；逐 token decode 尾部通常缺少跨请求复用价值。
  2. prepare_store() 过滤已经存在的 key，按 LRU/ARC 等策略腾出 CPU block。被 load 锁定或仍在写入的 block 不可驱逐；空间不足时可放弃本次 store。
  3. Scheduler 将“GPU 源 block → CPU 目标 block”的 job 写入 connector metadata；Worker 在本地 CUDA stream 上执行异步 GPU→CPU DMA。控制消息不携带 KV 字节。
  4. store 是 best-effort：失败最多导致将来一次 cache miss 和重算，不应阻塞请求完成。实现还会把真正提交推迟到后续 engine step 的合适位置，减少与采样关键路径争用。
  5. 多层模式在 CPU 数据就绪后，再异步 cascade 到 FS/OBJ/P2P。CPU 被淘汰不代表 secondary 中的数据也必须消失。

11.2 一次 load：四态 lookup 与两段提升

表 11-1　KV offloading lookup 状态与调度行为

11.3 容量、角色与配置边界

  • cpu_bytes_to_use 是 CPU primary 的显式预算，文档定义为跨全部 Worker 的总量，不是“每 Worker 各一份”，也不会因挂载 secondary 自动变大。
  • secondary 有自己的容量约束：FS 受目录所在盘限制，OBJ 受 bucket/配额限制，P2P 受远端缓存限制。它们扩展总容量，但不扩展 pinned CPU 热层。
  • 单实例既保存又加载时通常使用 kv_role="kv_both"。这里的角色与 PD 中固定 P/D 实例的部署语义不同。
  • secondary 不是 Manager 自动扫描出来的；TieringOffloadingSpec 读取配置，经 factory 构造 tier 对象并显式注入 Manager。Manager 只依赖 lookup / submit_store / submit_load / get_finished_jobs 等接口。

11.4 精确边界：哪些 chunk 可 store，哪些 hit 可 load

  • store 不是任意尾巴都写：候选通常要形成已完成、可哈希、按 connector chunk/block 对齐的区间；prompt-only 配置会排除 decode 尾部。已存在、正在写、被 load 锁定、容量不足或没有可驱逐 victim 的 key 会被过滤/跳过。
  • load 取连续最长前缀：Scheduler 必须让 local prefix、external prefix、cache group/hybrid state、sliding-window 与 partial tail 在同一可恢复边界上达成一致；不能只因“某个远端 hash 命中”就把后面不连续的 block 也算成已计算。
  • 元数据账本不等于 DMA 已完成：Scheduler 知道 job、tier 与 block ownership，但 GPU↔CPU 的真实完成仍由 Worker 的 KVConnectorOutput 回报；secondary tier 的异步 promotion/store 也要由 manager 的 get_finished_jobs() 轮询推进。
  • 失败语义不同：best-effort store 失败通常退化为未来 MISS；load 失败必须阻止请求读取未就绪 KV，并选择重试、重新计算或报错。
作用域
“GPU ↔ pinned CPU primary ↔ secondary”是当前内置 OffloadingConnector + TieringOffloadingSpec 的架构，不是所有自定义 KV connector 的宇宙定律；其他 connector 可以采用不同的数据路径，只要满足统一 lifecycle contract。
为什么 hot decode 仍要求历史 KV 常驻 HBM？
Paged/Flash attention 的确会把历史 KV 从 HBM 分块流入片上 SRAM，用 online softmax 一块一块算；但这只节省 SRAM，不减少整条历史 KV 的 HBM 容量，也不减少每个 decode step 的总读取量。若每块都临时从 CPU/磁盘取回，PCIe/存储等待会反复进入 TPOT。Offloading 适合“整段前缀在请求开始前换入”，不适合“每个 token 边算边从慢层分页”。

第四部分 · 性能、观测与源码实验

12. 性能模型与调参：先判断瓶颈，再动参数

vLLM 的参数不是“越大越快”的旋钮。一个设置可能提高稳态吞吐，却放大 TTFT、显存占用或 P99；也可能只把瓶颈从 GPU 移到 NCCL、CPU tokenizer、网络或 Parser。最可靠的方法是用真实 prompt/output 长度分布和并发曲线，分别测 queue、prefill、decode、KV transfer 与前端开销。

12.1 指标定义与一阶性能模型

\[ \begin{aligned} \mathrm{TTFT}&=t_1-t_0,\\ \mathrm{ITL}_j&=t_j-t_{j-1},\qquad j=2,\ldots,N,\\ \mathrm{TPOT} &=\frac{1}{N-1}\sum_{j=2}^{N}\mathrm{ITL}_j =\frac{t_N-t_1}{N-1},\\ T_{\mathrm{E2E}}&=\mathrm{TTFT}+(N-1)\mathrm{TPOT}. \end{aligned} \]

\(t_0\) 是请求进入统计边界的时刻，\(t_j\) 是客户端观察到第 \(j\) 个输出 token 的时刻。普通逐 token decode 时，单个 ITL 才可近似拆成下式；spec decode、collector 合并与 stream_interval 会破坏 GPU step、前端迭代与 token 的一一对应。

\[ \mathrm{ITL}_j \approx T_{\mathrm{schedule/IPC}}^{(j)} +T_{\mathrm{decode}}^{(j)} +T_{\mathrm{collective}}^{(j)} +T_{\mathrm{sample}}^{(j)} +T_{\mathrm{output}}^{(j)} . \]
\[ T_{\mathrm{TTFT}}^{(\mathrm{PD})} \approx T_{\mathrm{proxy,in}}+T_{\mathrm{queue,P}} +T_{\mathrm{service,P}}^{(\mathrm{max\_tokens}=1)} +T_{\mathrm{handoff}}^{(\mathrm{crit})} +T_{\mathrm{queue,D}}+T_{\mathrm{first,D}}+T_{\mathrm{proxy,out}} . \]

示例 Proxy 的 P 侧 max_tokens=1 仍会采样一个 token，因此归入 \(T_{\mathrm{service,P}}\)；\(T_{\mathrm{handoff}}^{(\mathrm{crit})}\) 只计算无法与其他工作重叠、真正落在关键路径上的 KV 搬运与同步时间。

\[ \begin{aligned} |\mathcal R_k|&\le S_{\max},\\ \sum_{i\in\mathcal S_k}n_{i,k}&\le B_{\mathrm{sched}},\\ \sum_{i\in\mathcal S_k}(n_{i,k}+d_i)&\le B_{\mathrm{batch}},\\ L_i&\le L_{\max}. \end{aligned} \]

\(B_{\mathrm{sched}}\) 对应显式 max_num_scheduled_tokens（未设置时继承 batch token budget），\(B_{\mathrm{batch}}\) 对应 max_num_batched_tokens，\(d_i\) 是 speculative draft slots。因而“本 step 调度预算”和“ModelRunner 输入预算”在启用 spec decode 时不应混为一个量。

Flash/Paged attention 会把 HBM 中的 KV 分块送入 SRAM，并不一次 materialize 完整注意力矩阵；但每个 decode step 仍需遍历相关历史 KV。分块解决片上内存问题，不消除 HBM 容量与带宽成本。

\[ \begin{aligned} Q_{\mathrm{KV}}^{(r)} &\approx s_{\mathrm{KV}} \sum_{i\in\mathcal D_k}L_i \sum_{\ell\in\mathcal L_r} H_{\mathrm{KV},\ell}^{(r)}(d_{K,\ell}+d_{V,\ell}),\\ T_{\mathrm{step}} &\gtrsim \max\!\left( \frac{F}{P_{\mathrm{eff}}}, \frac{Q_{\mathrm{HBM}}}{\mathrm{BW}_{\mathrm{HBM}}}, \frac{Q_{\mathrm{comm}}}{\mathrm{BW}_{\mathrm{comm}}} \right). \end{aligned} \]

这是 roofline 风格的下界：prefill 往往更接近计算项，长上下文 decode 更容易被 KV/HBM 项主导，而跨节点 TP 还会放大通信项。真实 step 还叠加调度、kernel launch 和前端开销。

12.3 三个 batch 参数如何互相制约

  • max_num_seqs 限制 batch 的“宽度”：decode 并发通常首先受它和 KV 容量约束。
  • max_num_batched_tokens 限制单 step 的“厚度”：prefill 常先用完这个预算；调大可提高吞吐，也会让单步更长并影响延迟公平。
  • max_model_len 限制单请求的“长度”：它同时影响最坏 KV 需求，却不表示每个请求启动时就预留满长度。

未启用 chunked prefill 时，max_num_batched_tokens 必须至少覆盖 max_model_len；始终需要 max_num_batched_tokens ≥ max_num_seqs，否则每个 decode 请求连每步 1 token 都无法保证。启用 chunked prefill 后，长 prompt 可跨 step 推进，从而解耦单请求长度与单步 token 预算。

B200 应不应该手动写 16K？
当前源码按“设备显存 ≥ 160 GiB”的硬件档（注释举 B200/B300）把在线和离线的默认 max_num_batched_tokens 设为 16384，max_num_seqs 设为 1024。这里是按容量档位判断，并不假设所有 B200 只有一种固定显存规格；16384 是自动默认起点，不是所有负载的普适最优值。performance_mode=throughput 还会在用户未显式覆盖时把这两个默认值翻倍。

12.4 显存预算：不要套固定比例

gpu_memory_utilization 当前默认是 0.92，它给单个 vLLM 实例设总预算；权重和非 KV 开销经过加载、profiling 后，剩余部分才决定可分配 KV block 数。不同模型、dtype、量化、CUDA graph、并行方式和多模态缓存都会改变构成，因此不存在官方固定的“权重 x%、激活 y%、KV z%”配方。若设置 kv_cache_memory_bytes，它会绕过基于 utilization 的 KV 容量推导。

12.6 一个可复现的调优顺序

  1. 固定工作负载。 保存 prompt/output 长度分布、并发到达过程、是否共享前缀、是否 tool/reasoning、SLO（TTFT、TPOT、P99）。
  2. 建立单副本基线。 记录 tokens/s、request/s、GPU util、HBM/SM 活跃度、KV 使用率、prefix hit、preemption 和 CPU event-loop 延迟。
  3. 先消除容量错误。 验证模型能装下、KV block 足够、没有频繁抢占重算；再讨论吞吐。
  4. 只改一个主旋钮。 先扫描 max_num_batched_tokens 与 max_num_seqs，画吞吐—TTFT—TPOT Pareto，而不是只取 tokens/s 最大点。
  5. 再选并行。 模型装得下时避免无必要 TP；跨节点优先评估 PP/DP；用真实 NCCL 拓扑验证。
  6. 最后引入复杂机制。 只有重复前缀足够多才上 offload，只有混部干扰大于 KV transfer 成本才上 PD；每加一层都做故障和冷启动测试。
  7. 从新进程复测。 包括模型 reload、缓存冷/热两组、长时间稳态和客户端断连；不要只相信单次 warm benchmark。

调度、停滞与验证策略

13.4 用 batch > 1 验证 continuous batching

下面的实验同时发送四个不同长度的请求。你要记录的不是“每轮是不是四个请求各产一个 token”，而是每个 scheduler step 的 scheduled_new_reqs、scheduled_cached_reqs、每请求 num_scheduled_tokens 和 EngineCoreOutputs.outputs。它们往往并不一一对应。

import asyncio
from openai import AsyncOpenAI

async def one(client, index, prompt):
    stream = await client.completions.create(
        model="your-model-name",
        prompt=prompt,
        max_tokens=24,
        temperature=0,
        stream=True,
    )
    pieces = []
    async for event in stream:
        pieces.append(event.choices[0].text)
    return index, "".join(pieces)

async def main():
    client = AsyncOpenAI(base_url="http://127.0.0.1:8000/v1", api_key="x")
    prompts = [
        "用一句话解释 KV cache。",
        "先列出三个关键点，再解释 continuous batching。",
        "把 PagedAttention 与操作系统分页作类比，但指出类比边界。",
        "简述 TP、PP、DP 的区别。" * 8,
    ]
    results = await asyncio.gather(
        *(one(client, i, prompt) for i, prompt in enumerate(prompts))
    )
    for index, text in sorted(results):
        print(index, text)

asyncio.run(main())
预期现象不是固定时间表
短 prompt 可能较早进入 decode，长 prompt 可能被 chunked prefill 分多步处理；新请求可插入旧请求的 decode batch；显存紧张时请求还可能被抢占并重算。硬件、模型、预算和到达时刻都会改变具体排布。

14. 总结：三个账本与四个跨层契约

vLLM V1 的复杂度来自并发、异步和大量可选特性，但核心并不是一组互不相关的技巧。普通生成、spec decode、PD、Offloading 与 Parser 都必须让三个账本最终一致：Scheduler 的请求进度、KV manager 的资源所有权、Worker 的执行状态。异步只允许这些账本暂时存在 in-flight 差额，不允许它们失去可校正的对应关系。

以下问题来自学习对话里反复出现的困惑。答案刻意保持短，但给出足以继续追源码的边界。

1. Scheduler 为什么看起来没有明确写“这是 prefill / 这是 decode”？

因为 V1 尽量把二者统一成“这个请求还差多少 token 计算，本 step 给它多少 token 预算”。是否处于 prompt 计算、chunked prefill、普通 decode 或 spec decode，要结合 num_computed_tokens、prompt 长度、scheduled token 数和状态判断，不能只靠一个布尔标签。

2. num_scheduled_tokens == 1 就是 decode 吗？

不是可靠判据。prefill 的最后一个 chunk 也可能只剩一个 token；spec decode 或某些优化下 decode 一步可能涉及多个 token。它只说明本 step 给该请求安排了多少 token。

3. scheduled_new_reqs 是不是等于 prefill 请求？

不是。它表示这个 Worker 第一次接收该请求的完整状态。新请求随后可能执行 prompt token，也可能受 prefix/remote KV 等影响。cached/resumed 则描述 Worker 侧状态同步方式，不是纯粹的推理阶段标签。

4. block_ids 是 GPU 显存地址吗？

不是。它们是某个 KV cache pool 中的 block slot 索引。Worker 根据 pool layout、layer 和 rank 把索引映射到实际张量切片；它既不是 CUDA 指针，也不是 GPU 物理页号。

5. 一个请求的 block table 在所有 TP rank 上相同吗？

控制层通常下发相同的逻辑 block slot 序列，但每个 rank 的 KV pool 存的是该 rank 所负责的 heads/分片。相同 slot id 表示同一逻辑 token 区间在各 rank 本地 pool 的对应位置，不表示它们共享同一块物理显存。

6. block size 是“每块多少字节”吗？

配置中的 block size 首先表示每个 KV block 容纳的 token 数。其字节数还取决于层数、K/V、head 数、head size、dtype、并行切分和具体 KV layout。

7. prefix cache 命中后为什么还可能重算一个 token？

要产生下一个 token 的 logits，需要有一个合适的 query/最后位置参与 forward。某些远端 KV 或全前缀命中路径会保留或回退最后一个 token 重算；这不是 KV 传输失败，而是采样边界的需要。

8. HBM 不够时 vLLM 会把当前请求自动换到 CPU 吗？

不能笼统这么说。常规 V1 调度在 KV blocks 不足时主要使用 recompute preemption：释放请求 KV、重置进度并重新排队。KV offloading/connector 是额外机制，必须明确启用并遵循各自状态机。

9. gpu_memory_utilization 应该固定设成 0.9 吗？

当前快照默认值是 0.92，但它是实例可使用显存的目标比例，不是“KV 固定占 92%”。权重、执行峰值、CUDA graph、非 torch 分配和安全余量共同决定最后可切多少 KV blocks。应以 profile 结果、OOM、抢占率和实际负载调参。

10. 为什么不能给权重、activation、KV 一个通用固定比例？

权重由模型和量化决定，activation 峰值由 batch/token budget/backend 决定，KV 又受上下文长度、并发、dtype 和并行切分影响。固定百分比最多是某台机器某个配置的观测，不是架构公式。

11. EngineCore 和 Worker 是严格一问一答的 ping-pong 吗？

不是。当前提交在配置兼容时会自动启用 async_scheduling：batch queue 允许多个 batch 在途，CPU 可在 GPU 执行 N 时调度 N+1，forward 与 sampling 也可能拆开。只有关闭异步或遇到不兼容组合时，时序才更接近 schedule → execute/sample → update 的单批闭环。

12. MultiprocExecutor 的 Worker 都收到完全相同的内容吗？

它会广播共同的调度控制对象，但 rank、本地权重分片、PP stage、connector metadata 和本地张量语义会让各 Worker 执行不同局部工作。“同一控制消息”不等于“相同数据和相同指令轨迹”。

13. SPMD 是否要求所有 rank 严格锁步？

不要求每条 Python 指令同时执行，但同一 collective group 必须以一致顺序进入匹配的集合通信。一个 rank 提前异常或走错分支，其他 rank 常表现为在 collective 处等待。

14. TP 的 all-reduce 到底发生在哪里？

以典型 attention 为例，QKV 常按输出/head 维切分，各 rank 独立计算本地 heads；O projection 常按输入维行切分，各 rank 产生部分和，然后做归并。具体位置会受 GQA、MLA、量化、sequence parallel、DCP 等改变。

15. PD 分离是不是一种 DP？

不是。PD 按推理阶段拆分资源，DP 复制完整服务能力来扩吞吐。二者正交：P 池和 D 池内部都可再使用 TP/PP/DP。

16. kv_producer 是否永远不能 decode，kv_consumer 是否永远不能 prefill？

不是绝对执行禁令。它们描述 connector 能力与部署意图。producer 收到普通请求仍可能完整生成；consumer 在没有可用远端 KV、传输失败或策略选择重算时，也可能本地计算 prompt。

17. PD proxy 把 max_tokens=1 发给 P，真的完全不 decode 吗？

它通常会在完整 prefill 后采样一个 token，只是代理主要使用返回的 KV 传输参数，不使用该文本结果。教程或容量估算不能把这一步写成“零采样”。

18. D 侧已经分配 blocks，为什么还要进入 WAITING_FOR_REMOTE_KVS？

slot 预留只解决“数据到哪里”，不代表 NIXL backend 的传输/拷贝已经完成。等待状态阻止模型读取未就绪的 KV；Worker 完成传输并回报后，Scheduler 才把请求重新提升为可运行。

19. NIXL 是否固定使用一种数据面 backend？

不是。数据搬运是核心，但实际 backend/plugin 默认是 UCX，也可按构建与配置选择 LIBFABRIC、GDS 等；即便选择 UCX，最终 transport 仍取决于环境与拓扑，RDMA 只是可能路径之一。完整流程还包含 side channel 握手、agent metadata、兼容性校验、TP 映射、完成通知与 lease 回收。把 NIXL 直接画成一条固定 RDMA 箭头，会同时漏掉控制面和 backend 可配置性。

20. KV offloading 与 prefix caching 是一回事吗？

不是。prefix caching 判断当前 KV pool 中是否有内容相同的可复用 blocks；offloading 把 KV 保存到 CPU/外部 backend，并在以后显式查找和载入。二者可协作，但所有权、生命周期和代价不同。

21. 同机 shared-memory RPC 是否完全零拷贝、零序列化？

不能这么概括。实现可让部分 payload 通过共享内存 ring，ZMQ 负责通知或溢出路径，但 Python 对象仍可能 pickle，生产者/消费者也可能发生内存复制。多模态 tensor 的 OOB 共享内存还依赖具体配置和队列可用性。

22. EngineCore 为什么不直接 detokenize？

当前边界让 EngineCore 保持 token-level 协议，前端为每请求维护 tokenizer 增量状态、stop-string 检查和输出模式，并服务同步/异步上层。这是合理的架构选择，不是理论上唯一可行的位置。

23. detokenizer.update() 会直接返回本次文本吗？

当前实现中它更新每请求状态并返回命中的 stop string；真正要发布的 delta/cumulative text 在构造 CompletionOutput 时从 detokenizer 状态取得。

24. async for res in engine.generate(...) 是否每次就是一个 token、一个 GPU step？

不是。一次前端 RequestOutput 可能合并多个 EngineCore 输出；spec decode 一步可出多个 token，stream_interval 和 collector 会合并，detokenizer/parser 也会暂扣内容。反过来 role、usage、finish、[DONE] 帧又可能不对应新 token。

25. tokenizer 已经把 token 变成文字，为什么还要 parser？

tokenizer 只恢复字符序列；parser 再解释模型约定的结构化语法，把文字拆成 content、reasoning 和 tool calls，并增量组装 JSON arguments。最后 serving 才把这些字段包装成 OpenAI 协议。

26. vLLM 会从输出 token 自动猜应该使用哪个 tool parser 吗？

通常不会。parser 由启动配置、模型适配与注册表选择；流式时每个 choice 维护自己的解析状态。配置错 parser，tokenizer 解出的文字可能仍正确，但结构化字段会错误。

27. GPT-OSS 也走 DeepSeek 的 ParserEngine 吗？

不是。GPT-OSS 使用 Harmony 相关解析路径。DeepSeek 的 DSML/ParserEngine 只能按其实际 scanner、lexer 和状态机实现来讲，不应把某个模型族的语法泛化给所有模型。

28. ParserEngine 与 xgrammar 是同一个东西吗？

不是。serving 侧 ParserEngine 解释已经生成的文本/标记；structured outputs 使用的 xgrammar 在生成阶段约束允许采样的 token。一个是输出解释，一个是生成约束。

29. Pooling 是否就是把整段文本压成一个 embedding？

不总是。pooling 类任务包括 embed、classify，也包括逐 token 的 token_embed/token_classify 等；输出可是一条向量、类别结果或逐 token Tensor。它不走自回归 decode，但长输入仍可能被 chunked prefill 分成多个 step。

30. EngineClient 与 EngineCoreClient 有什么区别？

EngineClient 是 serving 面对的高级生成/编码接口，当前主要实现是 AsyncLLM；EngineCoreClient 是前端与后台 EngineCore 通信的低级接口，有 in-process、sync/async multiprocess 和 DP 变体。client 对象本身不等于一个独立进程。

31. StreamingInput 只是为未来实时音频预留的吗？

不是。它已有实际实现和测试，只有当 prompt 本身是 AsyncGenerator[StreamingInput] 才进入该分支；普通 Chat/Completion 不会自动走它。当前仍有 pooling、n>1、stop strings 等能力限制。

32. B200 应该按多少 GB 估算？

不要把“B200”写成一个永远固定的容量数字。当前配置逻辑更适合按“至少 160 GiB 的硬件档位”讨论，再以实际设备查询结果做容量计算。

33. 一条经验能否直接推广到所有 ModelRunner？

不能。聊天里很多观察来自经典 GPU ModelRunner v1；ModelRunner v2、PP、异步调度、pooling、multimodal、Mamba/混合 KV 等路径会改变 request state、buffer 和下发字段。先确认当前 runner 与 feature gates。

34. FCFS 下 cache pending 的队头会堵住所有后续请求吗？

不会。当前实现把本 step 暂时不可运行的请求放到 skipped_waiting，继续扫描后续 ready 请求；下一 step 再优先重查。它避免 head-of-line blocking，但不承诺严格完成顺序或绝对无饥饿。

35. Ray V2 的 TCPStore 会传模型权重、激活或 KV 吗？

不会。它用于 torch.distributed rendezvous/进程组初始化。权重由各 Worker 从本节点可达的存储加载，GPU tensor 热路径由 NCCL、pipeline P2P 或所选 all-to-all backend 承担。

36. DP+EP 时每个 DP rank 还是完整独立模型吗？

不能再这样概括。dense/non-EP 时 DP 可视为完整副本；DP+EP 时 attention 等部分可复制，但 expert weights 与 routed tokens 跨 TP×PCP×DP ranks 分片/通信。

37. output_rank 是否表示只有该 rank 执行 Worker RPC？

不是。所有 Worker 都执行 (method,args,kwargs,output_rank)；该字段只决定哪些 rank 回包。普通模型输出收一个 rank，connector aggregator 场景可收齐所有相关 rank。

38. 非流式请求是不是直到最后才 detokenize？

不是。它每 step 仍更新 detokenizer，只是 FINAL_ONLY 让未结束的 make_request_output() 返回 None；结束时才把累积全文和全量 token IDs 交给 parser.parse()。

39. parse_delta() 只收到增量，历史一定在 _stream_state 吗？

不一定。legacy parser 在 StreamState 累积全文；ParserEngine 把语法历史放在 lexer/scanner/slots；Harmony 用自己的 StreamableParser。共同点是 parser 对象按请求/choice 保持状态。

40. 开启 PD 就一定提高吞吐吗？

不一定。官方当前仍把该能力标为 experimental，并明确指出 disaggregation 本身不提升 throughput；价值主要是隔离干扰、独立扩缩容和改善特定 SLO，必须把第二份权重、Proxy 与 KV transfer 成本算入。
